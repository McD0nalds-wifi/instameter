# Ревью PR по правилам проекта

Правила ревью живут в документации проекта; скилл их не содержит и не пересказывает —
он определяет порядок чтения и формат результата. Нормативный свод — `docs/code-review.md`,
механика («почему так») — в доменных доках.

## Шаг 1: правила — ДО диффа

1. Прочитай `docs/code-review.md` ЦЕЛИКОМ. Это полный чеклист; читается до анализа кода,
   иначе мнение о диффе сложится раньше правил и правила применятся вполсилы.
2. Не пересказывай правила по памяти: в замечании цитируй формулировку и указывай раздел.

## Шаг 2: собери дифф

- По умолчанию — текущая ветка против `main`: `git diff main...HEAD` (от merge-base).
- Если назван PR/ветка — возьми их; незакоммиченное — `git diff HEAD`.
- Большой дифф дели по файлам, а не режь молча: каждое изменение должно быть просмотрено.

## Шаг 3: доменные доки через doc-map — за механикой

По `docs/doc-map.json` подбери доки под дифф:

1. **`codePaths`** — доки, чьи глобы покрывают изменённые пути (это же требование хука).
2. **`keywords`/`summary`** — доки по темам диффа: движок и формулы → exposure-engine,
   типы и IndexedDB → data-model, стили и тема → styling, service worker и сборка →
   deployment, слои и гидратация → architecture, тесты → testing.
3. Читай по правилам скилла `doc-map-reading` (без перечитывания уже прочитанного).

Доки здесь — источник механики для глубины ревью: они дают увидеть баги, которых нет
в чеклисте (поток данных, кламп выдержки, миграции, precache), и убивают невежественные
придирки. Сомневаешься в замечании — сначала проверь механику по доке, потом пости.

## Шаг 4: проверка диффа

- Прогони КАЖДОЕ изменение по чеклисту и по правилам/механике прочитанных доков.
- Не дублируй линтеры: чеклист покрывает только то, что eslint/steiger не ловят.
  Сомневаешься — `yarn lint` или `yarn steiger` вместо замечания.
- Смотри не только на строки диффа: файл, который импортируется, но не добавлен в PR;
  дока, которая описывает изменённый механизм, но не обновлена (реверс-мапа `codePaths`
  в `doc-map.json` — детектор); правка `.md` без пересборки `yarn doc-map`.
- Мелкие механические правила (import type, скобки, нейминг) проверяй отдельным проходом
  по чеклисту — они теряются, когда внимание занято логикой.

## Шаг 5: противоречия источников

Если чеклист и доменная дока расходятся — это баг синхронизации документации:
вынеси замечание с обеими формулировками, не решай сам, какая права.

## Шаг 6: отчёт

- Язык — русский. Формат: `файл:строка` → что нарушено → правило (док + раздел, цитата) →
  как починить (кодом, если уместно).
- Сортировка по серьёзности: ломает поведение → архитектура → читаемость.
  Похвалы и пересказ диффа не пишутся.
- Замечание без правила в доках допустимо только для явного бага — помечай «вне чеклиста».
- Самопроверку своей же ветки, написанной в этой сессии, лучше гонять свежим субагентом:
  автор наследует свои слепые пятна, чужой контекст — нет.
