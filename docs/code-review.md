# Правила для код-ревью

Полный чеклист для ревью кода в instameter. Покрывает только то, что ESLint, Steiger
и TypeScript не ловят автоматически. Сомневаешься — `yarn lint` или `yarn steiger`
вместо замечания.

## 1. FSD-архитектура

- Импорты только сверху вниз: `app → pages → widgets → features → entities → shared`
- Нет кросс-импортов между слайсами одного слоя
- Каждый нетривиальный компонент — в своей поддиректории (camelCase)
- Корневой компонент страницы — прямо в `ui/`, без обёртки
- Public API (`index.ts`) — на уровне слайса, не внутри `ui/`
- Слайсы называются по сущности (`myCameras`, не `myCamerasList`), компонент страницы —
  с суффиксом `Page` (`MyCamerasPage`)
- В `app` нет сегментов `ui` и `providers`: UI оболочки живёт в `widgets/appShell`
- Движок рекомендаций (`shared/lib/exposure`) не импортирует React, Jotai и IndexedDB

## 2. TypeScript

- `strict` и `noUncheckedIndexedAccess` — не отключать
- `import type { Foo }` для типовых импортов
- Типы из React импортировать напрямую: `import type { ChangeEvent } from 'react'`, не `React.ChangeEvent`
- Функции — стрелочные выражения: `const foo = () => {}`
- React-компоненты — `const MyComponent: FC<Props> = ({ prop }) => {}`
  - **Не** `const MyComponent = ({ prop }: Props) => {}`
- Типы данных выводятся из схем valibot (`v.InferOutput`), а не дублируются руками

## 3. Стиль кода

### Именование параметров

Не сокращать имена параметров: `event` вместо `e`, `error` вместо `err` и т. д.

### Колбэки

Именованные колбэки вместо инлайн-лямбд при нетривиальной логике:

```tsx
// правильно
const reloadWithNewVersion = () => void updateServiceWorker(true);
<Button onPress={reloadWithNewVersion} />
// неправильно (нетривиальная логика)
<Button onPress={() => void updateServiceWorker(true)} />
```

### Итерация

Методы массивов (`map`, `filter`, `reduce`, `find`, `some`, `every`, `forEach`),
не циклы `for` / `for...of`. Деструктуризация в `map`:

```tsx
// правильно
cameras.map(({ id, nickname }) => ({ value: id, label: nickname }))
// неправильно
cameras.map((camera) => ({ value: camera.id, label: camera.nickname }))
```

## 4. Стили и UI

Подробности — `styling.md`.

- Только Tailwind-классы, без CSS Modules и inline `style={{}}`
- Цвета только из токенов HeroUI; произвольные значения и палитра Tailwind запрещены линтером
- Текст — через Typography HeroUI, не сырые `<p>`/`<span>`
- Все строки интерфейса — в `shared/config/strings.ts`, не в компонентах
- Склонения — через `pluralize` (`Intl.PluralRules`), не конкатенацией
- Цели нажатия от 44 пунктов; решение не передаётся одним цветом

## 5. Состояние и данные

Подробности — `architecture.md` и `data-model.md`.

- IndexedDB — источник правды: запись идёт через write-атом, сначала в БД, затем в атом
- Всё, что читается из IndexedDB, проходит `safeParse`; битая запись пропускается
  с `console.warn`, а не роняет приложение
- Миграции только аддитивные: новая миграция добавляется в конец массива, существующие
  не меняются
- Новая настройка — отдельный ключ в `appSettings` со своей схемой и значением по умолчанию
- Сетевых запросов в рантайме нет. Любой `fetch` наружу — замечание

## 6. PWA

Подробности — `deployment.md`.

- Новые типы статических файлов — проверить, что они попадают в `globPatterns` и не дублируют
  то, что vite-plugin-pwa добавляет сам
- Изменения в `vite.config.ts`, затрагивающие base, манифест или service worker, — прогнать
  `yarn test:e2e`

## 7. Тесты

Подробности — `testing.md`.

- Тест-файлы в `__tests__/` рядом с модулем, формат `moduleName.test.ts(x)`
- Описания `describe`/`it` — на русском
- Один рендер на тест
- `userEvent` — только через `setupUser()`
- Компоненты с атомами рендерятся в своём Jotai `Provider` со свежим store
- Новая формула в движке — с тестом по эталонной таблице из `exposure-engine.md`

## 8. ESLint

### import/order

- Порядок: type → external → parent (`../`) → sibling (`./`) → internal (`@/`)
- `--max-warnings 0` — предупреждения тоже фейлят

### Выключенные правила

`sonarjs/null-dereference` и `sonarjs/argument-type` выключены глобально: оба переоткрывают
то, что уже доказывает `strict`, но без информации о типах, и дают ложные срабатывания.

`unicorn/no-useless-undefined` не проверяет тела стрелочных функций: иначе он конфликтует
с `@typescript-eslint/no-empty-function` на заглушках вида `() => undefined`.

**Точечных `eslint-disable` в коде нет ни одного.** Появившийся — повод разобраться с правилом
централизованно, а не подавлять его по месту: директива это ещё и комментарий, который
правило 9 запрещает. Если правило ошибается один раз — чинится код, если всегда — выключается
в конфиге.

## 9. Комментарии

- Комментариев в коде нет: любой `//`, `/* */` или JSDoc в диффе — замечание. Тесты, типы и
  поля интерфейсов не исключение
- Исключение — triple-slash директивы (`/// <reference types>`) и комментарий, который
  пользователь попросил явно
- Объяснение уезжает в доку из `docs/` (привязка — `codePaths` в `doc-map.json`), а код,
  который без пояснения не читается, переписывается: имя, выделенная функция, ранний `return`

## 10. Структура компонентов

- Render-функции внутри компонента — только в крайнем случае:
  ```tsx
  // плохо: ветвление спрятано в функции внутри компонента
  const renderContent = () => { if (isEmpty) return <EmptyState />; return <List /> };

  // хорошо: отдельный компонент с ранними return либо условный JSX по месту
  <Section>{<CamerasContent cameras={cameras} />}</Section>
  ```
  Исключение — render-пропсы библиотек
- Каждый подкомпонент — в своей поддиректории с camelCase

## 11. Документация

- Если изменение трогает код, привязанный к доке (через `codePaths` в `doc-map.json`), —
  проверь, что дока ещё актуальна; если нет — обнови в том же PR
- Правка `.md` без пересборки `yarn doc-map` — баг
- Решение, которое меняет SDLC (стек, модель данных, алгоритм), фиксируется в соответствующей
  доке, а не только в описании PR
