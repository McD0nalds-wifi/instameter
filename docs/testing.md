# Тестирование и верификация

Особенность проекта в том, что зелёные тесты ничего не доказывают. Можно безукоризненно
реализовать формулы и всё равно систематически промахиваться на полторы ступени — из-за
неверного допущения о том, как меряет телефон. Поэтому верификация строится в три слоя,
плюс отдельный автоматический слой для PWA.

## Слой 1. Юнит-тесты чистых функций

Vitest, без DOM. Расчёт EV по известным тройкам, предсказание выдержки, поведение на границах.
Эталон — таблица прогона в `exposure-engine.md`.

Обязательный кейс — кламп: при EV₁₀₀ = 16 для Lomo'Instant Wide экспокоррекция −1 не должна
менять остаточную ошибку ни на что. Если меняет — в коде путаница между «хочет» и «может».

## Слой 2. Золотой набор EXIF

Два-три десятка реальных снимков с разных телефонов и сцен, уложенных в репозиторий вместе
с ожидаемым EV. Ловит регрессии парсера и разнобой форматов: HEIC с iPhone, JPEG с Android,
снимок без `ExposureBiasValue`, снимок со стёртыми метаданными после отправки в мессенджере.

## Слой 3. Полевая проверка

Единственный слой, который действительно подтверждает продукт. План — две пачки плёнки на серию:

- калибровочная тройка — одна сцена при −1, 0 и +1 EV, чтобы вывести постоянную поправку телефона;
- семь сцен из таблицы алгоритма — от яркого солнца до комнаты вечером, по кадру на сцену;
- три сложных случая — контровой свет, тёмный объект на светлом фоне, вспышка на границе радиуса.

Каждый отпечаток оценивается по трёхбалльной шкале в одинаковом свете и глазами, а не по скану:
сканер и камера телефона подтянут яркость и соврут сильнее, чем сам замер.

**Критерий приёмки MVP:** из десяти кадров второй серии не более двух выходят за пределы
приемлемой экспозиции, причём приложение заранее предупредило о риске хотя бы по одному из них.

## Слой PWA. Smoke-тест офлайна

Офлайн — критерий успеха, и сломать его одной неудачной правкой конфига service worker очень
легко. Поэтому один Playwright-тест (`e2e/offline.spec.ts`):

1. собрать билд и поднять `vite preview`;
2. открыть приложение и дождаться активного service worker;
3. выключить сеть и перезагрузить страницу;
4. увидеть главный экран.

Тест гоняется только в Chromium. Safari на iOS он не покрывает, поэтому перед релизом остаётся
ручная проверка на телефоне: установка на главный экран, запуск в авиарежиме, замер с HEIC.

## Правила юнит- и компонентных тестов

- Окружение — happy-dom, Testing Library, jest-dom-матчеры, `globals: true`.
- Тесты лежат в `__tests__/` рядом с модулем, файл — `moduleName.test.ts(x)`.
- Описания `describe`/`it` — на русском языке.
- **Один рендер на тест.** Все проверки одного экрана — в одном `it` после единственного
  рендера. Отдельный `it` — только если нужны другие входные данные.
- **`userEvent` берётся через `setupUser()`** из `src/shared/lib/testing`, прямой
  `userEvent.click(...)` не используется. Хелпер выключает `pointerEventsCheck`: по умолчанию
  user-event на каждый вызов проходит `getComputedStyle` по цепочке предков, а в happy-dom
  реальных стилей всё равно нет.
- `*ByRole` допустим: экраны маленькие. Если DOM разрастётся и запросы станут медленными —
  переходить на `getByText` и `getByLabelText`.
- Компоненты, читающие атомы, рендерятся внутри своего Jotai `Provider` со свежим store, чтобы
  тесты не делили состояние.
- IndexedDB в тестах — `fake-indexeddb/auto`, база пересоздаётся между тестами.
- Сети в приложении нет, поэтому MSW не нужен.

## Команды

```bash
yarn test          # Vitest
yarn test:e2e      # Playwright: сборка, preview, офлайн
```
